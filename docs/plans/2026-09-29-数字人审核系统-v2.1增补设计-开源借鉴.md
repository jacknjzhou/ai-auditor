# 数字人审核系统 v2.1 增补设计 —— 开源借鉴（UniEmployee / StaffDeck）

> 版本 2026-09-29 · 基于 v2.0 详细设计（2026-09-28）与 ai-auditor P1 实现
> 借鉴来源：[UniEmployee](https://github.com/zj-unicom-ai/UniEmployee)（浙江联通，MIT）、[StaffDeck](https://github.com/OpenBMB/StaffDeck)（面壁智能/OpenBMB，AGPL-3.0）

## 0. 定位结论与借鉴决策表

两个开源项目均为**数字员工平台**（通用岗位构建/管理/渠道），ai-auditor 是**单一岗位（审核员）的旁路执行内核**——不构成竞品，借鉴的是它们把"数字人"当**组织成员治理**的工程范式。

| # | 借鉴点 | 来源 | 现状差距 | 改造 | 落点 |
|---|--------|------|---------|------|------|
| 1 | HITL 中断-恢复 run 模型 | UniEmployee | decided 即终态，人工处理不回流 | 任务升级为可挂起 run | §1（P1.5） |
| 2 | SOP 状态机化 | 两者共识 | S1–S4 硬编码 | FlowProfile 内可配置审核 SOP | §2（P1.5） |
| 3 | run 事件流 + 断线重放 | UniEmployee | 只有 llm_call/finding 留痕，无过程事件 | run_event(seq) 统一事件表 | §3（P1.5） |
| 4 | 反馈→评估闭环 | StaffDeck | 反馈表仅设计未闭环 | 周期评估 job + 放权建议 | §4（P2） |
| 5 | 文档结构感知检索 | StaffDeck | 条款平铺切片 | 制度文档层级索引（保留提交日过滤） | §5（P2） |
| 6 | 模型并发准入阀 | UniEmployee model_admission | 无并发保护 | Worker 侧 per-model 信号量 + 排队计数 | §6（P2） |
| 7 | 渠道适配器注册表 | StaffDeck 渠道内核 | 回写三档硬编码顺序 | channel adapter 注册表 | §7（P2/P3） |

**明确不做**（YAGNI，见 §8）：不做通用数字员工平台、不做会话聊天交互、不做 IM 渠道直接接入、不做沙箱执行（P3 评估附件解析沙箱）。

## 1. Run 挂起-恢复模型（借鉴 UniEmployee HITL）

### 1.1 状态机扩展

```
received → rule_eval → llm_chain → fusion → decided ──┬──► closed（无人工动作）
                                          │           └──► awaiting_human ──► resumed ──► closed
                                          └──→ failed
resumed 分支：SUPPLY_MATERIAL → 重入（增量）rule_eval/llm_chain → fusion → re-decided
             OVERRIDE_PASS / OVERRIDE_REJECT → 直接写终审决定 → closed
```

约束：
- `awaiting_human` 可超时（`due_at`），超时由兜底 job 提醒/升级（对齐 v2.0 §状态机超时兜底）；
- 一次 run 最多 N 轮挂起-恢复（默认 3），防死循环；
- `resume_token` 幂等：审批系统重复回调不产生二次恢复。

### 1.2 数据模型（新增/改造）

```sql
-- 从 escalation_log 分离"待办"语义（escalation_log 保留为回写流水）
CREATE TABLE human_task (
    id            UUID PRIMARY KEY,
    run_id        UUID NOT NULL REFERENCES audit_task(id),
    seq           INTEGER NOT NULL,               -- 挂起时的 run_event seq
    problem_codes JSONB NOT NULL DEFAULT '[]',
    assignee_role VARCHAR(64) NOT NULL,           -- 路由表目标节点
    assignee_user VARCHAR(64),                    -- 具体人（可空=按节点认领）
    options       JSONB NOT NULL DEFAULT '[]',    -- ["SUPPLY_MATERIAL","OVERRIDE_PASS",...]
    due_at        TIMESTAMPTZ,
    status        VARCHAR(16) NOT NULL DEFAULT 'pending',  -- pending|done|expired|cancelled
    resume_token  VARCHAR(64) NOT NULL UNIQUE,
    result        JSONB,                          -- {"action":..., "payload":..., "operator":...}
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at   TIMESTAMPTZ
);

-- 统一过程事件表（见 §3）
CREATE TABLE run_event (
    id         BIGSERIAL PRIMARY KEY,
    run_id     UUID NOT NULL REFERENCES audit_task(id),
    seq        INTEGER NOT NULL,                  -- run 内单调递增
    event_type VARCHAR(32) NOT NULL,              -- 见 §3 枚举
    payload    JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (run_id, seq)
);
```

### 1.3 恢复 API 与增量重审

```
POST /api/v1/audit-tasks/{run_id}/resume
Headers: X-Auditor-Signature（同 webhook 验签）
Body: {"action": "SUPPLY_MATERIAL|OVERRIDE_PASS|OVERRIDE_REJECT|COMMENT",
       "resume_token": "...", "operator": "u123",
       "payload": {"patch_fields": {...}, "comment": "..."}}
```

- `SUPPLY_MATERIAL`：payload 中 patch_fields 合并进 snapshot（版本 +1），按 SOP 状态机**只重跑受影响步骤**——规则层：全量重算（毫秒级）；LLM 层：仅重跑问题码对应的 S 步骤（S1 材料类/S2 一致性类问题重跑对应步骤，S3 若制度摘录未变可复用上轮结果并标注 `reused: true`）；
- `OVERRIDE_*`：不经流水线，直接写 `AuditDecision(level=..., matrix_reason={"cell":"human_override"}, confidence=None)` 并闭单；人工否决作为**负样本**进反馈表（§4）。

## 2. 审核 SOP 状态机化（借鉴 UniEmployee StateGraph / StaffDeck SOP）

### 2.1 SOP DSL（挂在 FlowProfile）

```json
{
  "sop_version": 1,
  "steps": [
    {"code": "S1", "engine": "llm", "prompt_id": "material_check",
     "run_when": {"op": "truthy", "left": "$ctx.has_attachments"},
     "on_fail": "skip", "next": "S2"},
    {"code": "R1", "engine": "rule", "rule_scope": "flow", "next": "S3"},
    {"code": "S3", "engine": "llm", "prompt_id": "policy_check",
     "needs": "rag", "next": "S4"},
    {"code": "H1", "engine": "human_approval", "when_finding": "major",
     "assignee": "$route", "next": "fusion"},
    {"code": "fusion", "engine": "fusion", "next": null}
  ]
}
```

- 引擎类型：`rule` / `llm`（prompt_id 引用 prompt 库）/ `rag` / `human_approval`（= 触发 §1 挂起）/ `fusion`；
- `run_when` 支持按快照条件跳步（如无附件跳过 S1）——直接解决"用章申请不需要 S2"这类按流定制需求；
- **零迁移兼容**：`FlowProfile.audit_sop` 为空时使用内置 SOP（等价现 S1–R–S2–S3–S4–fusion 序列），既有测试全部保持有效。

### 2.2 执行器

`worker/pipeline/sop/executor.py`：`SopExecutor(profile).run(ctx)` 替换 `audit_service` 中固定调用序；每步进入/退出写 `run_event`；`human_approval` 步骤返回挂起信号由 run 层处理。伪代码：

```python
step = sop.entry
while step:
    emit("step_started", step.code)
    if not eval_run_when(step, ctx):
        emit("step_skipped", step.code); step = next(step); continue
    result = ENGINES[step.engine].execute(step, ctx)      # 各引擎已有实现
    if result.suspend:                                     # human_approval
        return SuspendSignal(step=step.code, human_task=...)
    ctx.merge(result)
    step = sop.next(step, result)
```

## 3. run 事件流与断线重放（借鉴 UniEmployee agent_runs）

事件类型枚举：`run_created / step_started / step_skipped / step_finished / finding_added /
llm_called（含 latency、degraded）/ decision_made / suspended（含 human_task_id）/
resumed / writeback_attempted / writeback_result / closed`。

- 写入点：SOP 执行器与回写执行器内统一 `emit()`；`(run_id, seq)` 唯一约束保证单调；
- 查询 API：`GET /api/v1/audit-tasks/{id}/events?after=<seq>`（增量拉取，分页）；
- SSE 端点（P2）：`GET /audit-tasks/{id}/events/stream`——原型"审核中任务推进"动画的后端支撑，断线按 `Last-Event-ID` 补放；
- 取代分散留痕：`llm_call` 表保留（审计粒度更细），但过程叙事以 run_event 为准。

## 4. 反馈→评估闭环（借鉴 StaffDeck）

- 数据源：human_task.result（人工修正）+ 抽检结果 + OVERRIDE 样本；
- **评估 job**（Arq cron，周度）：输出指标——人机一致率、按问题码分桶的采纳/否决率、LLM 各步降级率、平均耗时；结果写 `eval_report` 表并生成报告页；
- **放权建议**：连续两周一致率 ≥ 阈值 → 建议提升 FlowProfile.mode（如 advisory→semi_auto）或放宽 amount_cap/conf_high；一致率跌破 → 建议降档。**建议必须人工确认后生效**（写 FlowProfile 时 version_no+1，全程留痕）——放权节奏从"手动配置"升级为"数据驱动的确认制"。

## 5. 制度知识库层级索引（借鉴 StaffDeck 结构感知）

- `knowledge_doc.structure`：解析制度文档为 树（章→节→条→款）；
- `knowledge_chunk` 增加 `path`（如 `第二章/第8条`）与 `level`；
- 检索两段式：先按 query 定位 2–3 个候选章节（结构信号），章节内再做向量×关键词 RRF（现检索保留）；引用输出带完整路径；
- **保留独有优势**：生效期按单据提交日过滤不变。

## 6. 模型并发准入阀（借鉴 UniEmployee）

- Worker 侧 `model_admission.py`：per-model `asyncio.Semaphore(n)` + Redis 计数排队（`admission:{model}`）；
- 超并发时任务**排队不拒绝**（审核为异步场景），排队时长写 run_event；
- 连续排队超阈值 → 告警（提示扩 worker 或换模型路由）。

## 7. 渠道适配器注册表（借鉴 StaffDeck）

- `worker/pipeline/routing/channels/`：`base.py` 注册表 + `mock/http` 已有，预留 `dingtalk/wecom/feishu.py` 骨架；
- 回写三档（FULL_API/COMMENT_ONLY/IM_ONLY）中的 IM 档从"硬编码顺序"改为**按 profile.writeback_config.channels 列表逐个尝试**，适配器自带幂等与重试。

## 8. P1.5 / P2 任务分解

### P1.5（1–2 周，代码级，验收=测试通过 + 内置 SOP 等价迁移零回归）

## 9. 风险与对策

- **复杂度风险**：SOP 状态机若配置失控会回到"平台化"歧路——约束：SOP 仅审核域内，不引入子代理/工具调用（那是 UniEmployee 的域）；
- **增量重审一致性**：复用上轮 S3 结果需在决策矩阵 reason 中标注 reused，审计可查；
- **事件膨胀**：run_event 高频写入——PG 按月分区预留，P1.5 先普通表 + 索引；
- **合规**：OVERRIDE_PASS 人工否决链路必须全程留痕（resume_token + operator + result），满足审计要求。
