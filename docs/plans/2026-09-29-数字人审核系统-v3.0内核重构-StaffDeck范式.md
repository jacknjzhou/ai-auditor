## 1. 重构依据：StaffDeck 本地实例的源码级分析

本地运行的 StaffDeck 桌面客户端（`D:\Programs\StaffDeck\staffdeck.exe`，Python/aiohttp 后端）虽已编译，但其执行内核通过 `_internal/app/llm/prompts/` 的 27 个完整 Prompt 与种子数据完全可考：

**三层执行内核**：

| 层 | StaffDeck 实现 | 核心契约 |
|---|---|---|
| Turn Planner / Router | LLM 每轮一次，输出 decision ∈ {continue_active, start_new_task, switch_to_pending, answer_only, clarify, handoff_human}，把复合诉求拆为**有序 task_frames** | 不选工具、不读 SOP 节点图；slot_hints 只存结构化字段，禁止存用户原文 |
| Harness Agent | 每个 TaskFrame 一个**隔离 AgentLoop**，串行动作协议 `action: tool \| finish` | TaskRequirement（goal / required_slots / completion_criteria）为唯一任务边界；能力两级：`available（已激活）/ catalog（紧凑目录）`，先 `capability_describe` 加载 schema 才可调用；知识检索硬预算（默认 2 次）；`required_capability_names` 未全部执行不得 completed；`awaiting_user` 挂起等槽位 |
| Response Generator | 汇总各帧 reply_fragment 合成最终回复 | memory_extractor / reflection 形成反馈闭环 |

**关键机制**：SOP 状态机（节点+边+allowed_actions，`handoff_human` 必须节点显式声明）、GeneralSkill 包（SKILL.md 工作流说明包 + 全生命周期管理）、能力三源同权（Skill/知识库/HTTP-MCP Tool 均为 Harness tool）、团队分派（execution_target=team_member + depends_on_task_ids + activation_condition）、run 事件流。

## 2. 总体架构：ai-auditor v3.0 三层执行内核

```
审批事件 webhook（幂等，不变）
        │
┌───────▼────────────────────────────────────────┐
│ ① AuditPlanner（对标 Turn Planner）              │
│  SOP 状态机 → 声明式展开为有序 TaskFrame 队列      │
│  每帧 = TaskRequirement 契约 + depends_on 依赖    │
└───────┬────────────────────────────────────────┘
        │ 逐帧派发（Arq 队列，无依赖帧可并行）
┌───────▼────────────────────────────────────────┐
│ ② Harness Agent（每帧一个隔离执行循环）            │
│  action: tool | finish 串行协议                  │
│  capability_manifest：available/catalog 两级     │
│  能力 = 规则查询 / 知识检索 / LLM核验 / 工具调用     │
│  knowledge_budget 硬预算 · awaiting_human 挂起    │
└───────┬────────────────────────────────────────┘
        │ 各帧 structured_result
┌───────┴────────────────────────────────────────┐
│ ③ Decision Composer（对标 response_generator）    │
│  汇总帧结果 → 决策矩阵融合（保留，最终 gate）        │
│  → 审核报告 → 回写计划 → run_event 全程留痕        │
└────────────────────────────────────────────────┘
```

## 3. 与 StaffDeck 的三处刻意差异（审核场景强化，已确认）

| # | StaffDeck | ai-auditor v3.0 | 理由 |
|---|---|---|---|
| 1 | Router 由 LLM 驱动（处理多轮会话模糊意图） | **Planner 确定性化**：SOP→TaskFrame 声明式展开，无 LLM | 单事件触发无意图歧义；省钱、可单测、零幻觉；LLM 预算全部留给 Harness 核验 |
| 2 | Harness 可自主发现全网能力（capability_search 全目录） | **能力白名单制**：catalog 仅开放当前 SOP 节点声明的强制/可选能力 | 合规场景步骤边界不可越；模型在步骤内自主（怎么查、检索几轮），步骤顺序由状态机 gate |
| 3 | finish 直接进回复合成 | **决策矩阵保留为最终 gate**：Composer 后置规则×置信度确定性融合 | LLM 结论永远只是建议信号，硬动作必须过规则 gate（v1.0 起的防幻觉机制，继承） |

## 4. 核心契约定义

### 4.1 TaskFrame（Planner 产出）

```python
@dataclass
class TaskFrame:
    frame_id: str                 # 服务端生成
    run_id: str                   # = audit_task.id，全链路 trace 锚点
    seq: int                      # 帧序号
    kind: str                     # rule_eval | llm_verify | knowledge_check |
                                  # risk_assess | human_gate | writeback
    requirement: TaskRequirement
    depends_on: list[str]         # 前置 frame_id；空 = 可立即并行
    status: str                   # queued/running/awaiting_human/
                                  # completed/failed/skipped
```

### 4.2 TaskRequirement（帧任务边界，对标 StaffDeck）

```python
@dataclass
class TaskRequirement:
    goal: str                          # 一句可验证的目标，如"核对住宿费是否符合标准"
    requirements: list[str]            # 可执行、可验证的子目标清单
    required_slots: dict               # 该帧所需输入槽位（从 snapshot 投影）
    completion_criteria: list[str]     # 完成判定标准
    required_capabilities: list[str]   # 强制能力，未全部执行不得 completed
    optional_capabilities: list[str]   # 可选能力白名单
    knowledge_budget: int = 2          # 知识检索硬预算
    failure_policy: str = "degrade"    # degrade | skip | halt
```

生成规则：**由 SOP 节点模板静态投影**（goal/requirements 来自节点 instruction 与 flow 上下文），不从用户消息抽取——与 StaffDeck 的本质差异之一。

### 4.3 Harness 动作协议

```json
// 调用能力（每轮至多一个，串行循环）
{"action": "tool", "tool_name": "knowledge_search",
 "arguments": {"query": "住宿费标准 一线城市"}}

// 结束帧
{"action": "finish", "status": "completed | awaiting_human | failed",
 "reply_fragment": "给 Composer 的结论草稿",
 "slot_updates": {}, "structured_result": {...},
 "task_summary": "帧执行摘要"}
```

- `retryable=false` 的工具错误禁止原样重试；
- 协议违规触发 `protocol_repair` 重试（对齐 StaffDeck repair 机制）；
- 每帧独立 transcript，只注入 TaskRequirement + capability_manifest + 当前 SOP 节点最小投影（current_step + next_steps）。

### 4.4 能力注册表（Capability Registry）

| capability | 说明 | 对应现有资产 |
|---|---|---|
| `rule_query` | 查询规则求值结果/预算余额/重复指纹 | 规则引擎 functions |
| `knowledge_search` | RAG 混合检索（生效期按单据提交日，硬预算） | worker/pipeline/rag |
| `llm_verify` | 材料核验/一致性核对（结构化输出） | LLM 链 S1/S2 拆分 |
| `llm_assess` | 制度符合性+风险评估，输出置信度 | LLM 链 S3/S4 拆分 |
| `doc_extract` | 附件 OCR/要素抽取（P3 预留） | preprocess 挂载点 |
| `writeback_probe` | 回写通道能力探测 | writeback tiers |

能力实现为**确定性 Python 函数**（非 prompt），`llm_verify/llm_assess` 内部才调 LLM——能力调用本身零幻觉。

## 5. SOP 状态机 schema（audit_sop v3，挂 FlowProfile.audit_sop）

```yaml
sop_code: expense_audit_v3
entry: intake
nodes:
  - id: intake
    kind: rule_eval
    instruction: 执行全部启用规则，产出确定性 findings
    required_capabilities: [rule_query]
    completion_criteria: ["全部启用规则已求值且 findings 落库"]
    transitions: [{cond: "always", next: material_check}]

  - id: material_check
    kind: llm_verify
    instruction: 核验发票/行程单材料真实性与一致性
    required_capabilities: [llm_verify]
    optional_capabilities: [knowledge_search]
    failure_policy: degrade          # LLM 不可用→降级为规则-only 信号
    transitions:
      - {cond: "hard_violation", next: "__reject__"}     # 终态保留字
      - {cond: "always", next: policy_check}

  - id: policy_check
    kind: knowledge_check
    instruction: 检索现行制度条款，逐项核对 findings
    required_capabilities: [knowledge_search]
    knowledge_budget: 3
    transitions: [{cond: "always", next: risk_gate}]

  - id: risk_gate
    kind: human_gate                 # 人工节点：声明后才可转人工
    instruction: 低置信度或重大违规时挂起等待实体人
    allowed_actions: [handoff_human, override, comment]
    transitions:
      - {cond: "awaiting_resolved", next: writeback}
      - {cond: "confident", next: writeback}

  - id: writeback
    kind: writeback
    required_capabilities: [writeback_probe]
    transitions: [{cond: "always", next: "__done__"}]
```

- `__reject__ / __done__` 为终态保留字；条件表达式复用规则 DSL 求值器（同一 engine，不引入第二套 DSL）；
- **空配置 = 内置等价 SOP**（intake→material→policy→risk→writeback，即现 S1–S4 链的状态机化），零迁移；
- Planner 展开算法：拓扑遍历条件边，确定性分支的帧直接生成；依赖运行时条件的（如 human_gate 后）生成**条件帧**，前置帧 finished 后由 Planner 二次展开。

## 6. 挂起-恢复与事件流（落地 v2.1 设计）

- **awaiting_human** = Harness `finish.status` 之一：帧置 `awaiting_human`，写 `human_task`（assignee/due_at/resume_token/options），run 状态 `awaiting_human`；人工动作（SUPPLY_MATERIAL/OVERRIDE/COMMENT）经 `resume_run()` 幂等恢复，仅重跑受影响帧（增量重审，S3 未变标 `reused`）；
- **run_event(run_id, seq 唯一)** 事件类型：`frame_planned / frame_started / capability_called / capability_result / protocol_repair / awaiting_human / frame_finished / composed / writeback_applied`——Planner/Harness/Composer 三层统一埋点，增量查询 API 先行，SSE 留 P4；
- `llm_call` 留痕表保留，作为 `capability_result` 的详细载荷。

## 7. 数据模型增量

| 表 | 说明 |
|---|---|
| `task_frame` | 帧 `(run_id, seq)` 唯一；kind/status/requirement(JSON)/depends_on/started_at/finished_at |
| `run_event` | `(run_id, seq)` 唯一；event_type/payload(JSON)/created_at |
| `capability_call` | capability/frame_id/arguments_digest/result_digest/latency_ms/budget_left（可并入 run_event，先独立成表便于预算审计） |
| `flow_profile.audit_sop` | 新增 JSONB 列，存 §5 schema |

其余（audit_task/finding/decision/human_task/escalation_log/knowledge_*/llm_call）全部沿用。

## 8. 保留资产映射表

| v2.x 资产 | v3.0 去向 |
|---|---|
| 规则引擎 DSL + 证据轨迹 | 能力 `rule_query`；条件边求值复用同一 engine |
| LLM 链 S1–S4（硬编码顺序） | **拆解**：S1/S2→`llm_verify`，S3/S4→`llm_assess`；执行顺序改由 SOP 声明 |
| RAG 混合检索 + 生效期过滤 | 能力 `knowledge_search`（预算制包装） |
| 决策矩阵 | Composer 内最终 gate，逻辑不变 |
| 转人工路由 + 回写三档降级 | human_gate 节点 + `writeback` 帧（路由表/降级链不变） |
| dispatcher/Arq/inline 降级 | 帧级派发复用同一队列设施 |
| webhook 幂等/验签 | 不变 |
| v2.1 human_task/resume/run_event 设计 | §6 直接落地 |

## 9. 实施路径（P3.0，基于现有代码）

| 任务 | 内容 | 验收 |
|---|---|---|
| T1 | TaskFrame/TaskRequirement schema + capability registry + Harness 循环骨架（串行协议+repair） | 单测：帧协议 12+ 用例 |
| T2 | AuditPlanner：SOP→帧声明式展开（含条件帧二次展开） | 单测：拓扑/依赖/保留字分支 |
| T3 | 内置等价 SOP 落地 + 五类节点引擎接入 | **51 现有测试零回归** + 等价迁移 case 逐一对齐 |
| T4 | run_event 全链路埋点 + capability_call 预算审计 | 一次完整 run 事件序列快照比对 |
| T5 | awaiting_human 挂起-恢复 + 增量重审（reused 标记） | 挂起→恢复→只重跑受影响帧 的端到端用例 |
| T6 | Decision Composer + 新示例 SOP（用章申请）验证"新流零代码接入" | 仅写 audit_sop YAML + 路由表即接入 |

节奏：T1–T3 为一批（内核），T4–T6 为一批（可观测与放权）。

## 10. 非目标（YAGNI）

- ❌ 会话式多轮 Router（无对话场景，Planner 保持确定性）；
- ❌ GeneralSkill 包生态 / SKILL.md 工作流包（审核能力是内置白名单，不需要第三方包）；
- ❌ 渠道接入（微信/企微/飞书直连）与团队多 agent 分派；
- ❌ 沙箱文件工具 / publish_artifact（无用户文件交付场景）。

以上均在出现真实需求时（P4+）再评估。
