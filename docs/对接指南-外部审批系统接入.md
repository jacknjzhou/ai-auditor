# 外部审批系统对接指南

> 版本 2026-09-30 · 对应代码 P3.0 · 协议已端到端实测验证
> 适用：任何需要接入 ai-auditor 数字人审核的 OA / BPM / 审批系统

## 0. 一句话总览

ai-auditor 是**旁路系统**，不改动你的审批系统。对接 = **两条腿**：

```
  ┌────────────────────┐   ① 推事件（你在审批节点触发）      ┌──────────────────┐
  │   你的审批系统      │ ──── POST /api/v1/webhooks/{src} ──▶ │                  │
  │  (OA / BPM / 钉钉) │      带 HMAC 签名 + Canonical 单据    │    ai-auditor    │
  │                    │ ◀─── POST {你的回写端点} ─────────── │                  │
  └────────────────────┘   ② 收回处置（打回/加签/附意见）      └──────────────────┘
```

- **① 入站**：单据到达关注节点时，把单据推给 ai-auditor（毫秒级返回 202，异步审核）；
- **② 出站**：ai-auditor 给出处置结果后，POST 到你提供的回写端点，你在自己系统里执行打回/加签/加意见。

你**不需要**部署 ai-auditor 内部的任何东西，只需要实现「发一个 HTTP 请求」+「收一个 HTTP 请求」。

## 1. 三个配置对象（对接前必须先就位）

| 对象 | 表 | 作用 | 目前如何配置 |
|---|---|---|---|
| 连接器 | `connector_config` | 声明一个接入源 + **该源的 HMAC 密钥** | ⚠️ 暂无 API，直接写 SQL |
| 流程档案 | `flow_profile` | 该审批流的放权档位 / 路由表 / 回写端点 / SOP | 部分有 API（SOP），其余写 SQL |
| 审核规则 | `policy_rule` | 该流的确定性规则（DSL） | ⚠️ 暂无 API，直接写 SQL |

```sql
-- ① 连接器：声明 source_code 与专属密钥（不配则回退 AUDITOR_WEBHOOK_SECRET_DEFAULT）
INSERT INTO connector_config (source_code, protocol, adapter_class, webhook_secret, enabled)
VALUES ('oa-a8', 'webhook', 'canonical', '<你的密钥>', true)
ON CONFLICT (source_code) DO UPDATE SET webhook_secret = EXCLUDED.webhook_secret;

-- ② 流程档案：放权档位 + 回写端点 + 路由表
INSERT INTO flow_profile (flow_code, mode, auto_pass_enabled, amount_cap,
                          writeback_tier, writeback_config, route_table)
VALUES ('expense_reimburse', 'semi_auto', true, 50000,
        'FULL_API',
        '{"http_endpoint":"http://your-oa.internal:8080/ai-audit/writeback"}'::jsonb,
        '[{"problem_codes":["HIGH_AMOUNT"],"target_node":"applicant","action":"RETURN","priority":1},
          {"problem_codes":["MISSING_RECEIPT"],"target_node":"applicant","action":"RETURN","priority":2},
          {"problem_codes":["POLICY_RISK"],"target_node":"fin_manager","action":"ESCALATE","priority":3}]'::jsonb)
ON CONFLICT (flow_code) DO UPDATE SET
    mode = EXCLUDED.mode,
    auto_pass_enabled = EXCLUDED.auto_pass_enabled,
    amount_cap = EXCLUDED.amount_cap,
    writeback_tier = EXCLUDED.writeback_tier,
    writeback_config = EXCLUDED.writeback_config,
    route_table = EXCLUDED.route_table;
```

> **关键**：`writeback_config.http_endpoint` 为空时，回写走 `MockWritebackAdapter`——
> **只记录、不真发 HTTP**。上线前务必确认它已指向你的真实端点，否则你会以为「回写了」其实没有。

SOP（可选，进阶）：若该流要自定义审核步骤，用 `config/sops/<flow>.yaml` 或管理 API 装载：

```bash
python -m app.cli load-sops                                   # 装载 config/sops/ 全部
curl -X PUT localhost:8300/api/v1/flows/expense_reimburse/sop -d @sop.json
```

## 2. 入站协议（你 → ai-auditor）

### 2.1 请求

```
POST /api/v1/webhooks/{source_code}
X-Auditor-Signature: sha256=<hex>
X-Auditor-Timestamp: <unix 秒>
Content-Type: application/json
```

`{source_code}` 即 `connector_config.source_code`，用于定位 HMAC 密钥。

### 2.2 签名算法（**最易踩坑处**）

```
expected = hex( HMAC_SHA256( secret, f"{timestamp}.{raw_body}" ) )
```

- `secret`：`connector_config.webhook_secret`，未配置则用 `AUDITOR_WEBHOOK_SECRET_DEFAULT`；
- `timestamp`：**参与的字符串就是头里那个值**（Unix 秒，不是毫秒）；
- `raw_body`：**原始请求字节**。⚠️ 必须签「你实际发出去的字节」——
  先序列化拿到 bytes，再对它签名，最后把**同一份 bytes** 发出去。
  如果签名后重新 `json.dumps`（改了分隔符/顺序/转义），签名必然校验失败。

时间窗：`|now - timestamp| ≤ AUDITOR_WEBHOOK_REPLAY_WINDOW_SECONDS`（默认 **300 秒**）。

```python
# Python 参考实现
raw = json.dumps(payload, ensure_ascii=False).encode("utf-8")
ts = str(int(time.time()))
sig = hmac.new(secret.encode(), ts.encode() + b"." + raw, hashlib.sha256).hexdigest()
requests.post(url, data=raw, headers={
    "X-Auditor-Signature": "sha256=" + sig,
    "X-Auditor-Timestamp": ts,
    "Content-Type": "application/json"})
```

```bash
# shell / curl 参考
BODY='{"source_system":"oa-a8",...}'   # 注意：curl --data 会原样发送
TS=$(date +%s)
SIG=$(printf '%s.%s' "$TS" "$BODY" | openssl dgst -sha256 -hmac "$SECRET" -r | cut -d' ' -f1)
curl -X POST "$HOST/api/v1/webhooks/oa-a8" \
  -H "Content-Type: application/json" \
  -H "X-Auditor-Signature: sha256=$SIG" -H "X-Auditor-Timestamp: $TS" \
  --data "$BODY"
```

### 2.3 报文结构（Canonical 单据）

```json
{
  "source_system": "oa-a8",
  "event_type": "SUBMITTED",
  "version": 0,
  "instance": {
    "instance_id": "IT-20260930-001",
    "flow_code": "expense_reimburse",
    "current_node": "fin_review",
    "submitted_at": "2026-09-30T18:02:32",
    "applicant": { "user_id": "u1001", "name": "张三", "dept_path": "总部/财务部" },
    "form": { "amount": 500000, "trip_reason": "客户支持", "budget_code": "B-2026-Q3" },
    "attachments": [
      { "file_id": "f-001", "file_type": "invoice",
        "uri": "https://oa.../f-001.pdf",
        "ocr_text": "住宿费 1200 元",
        "ocr_struct": { "total": 1200, "avg_hotel_price": 600 } }
    ],
    "ctx": { "submit_channel": "web", "dept_code": "FIN-01" },
    "std": { "hotel_cap": 500, "is_key_project": false }
  }
}
```

| 字段 | 必填 | 说明 |
|---|:---:|---|
| `instance.instance_id` | ✅ | 单据唯一 ID；缺失返回 **422** |
| `instance.flow_code` | ✅ | 与 `flow_profile.flow_code` 对应，决定用哪套档位/规则 |
| `instance.current_node` | ✅ | 当前节点，参与幂等键 |
| `event_type` | ✅ | `SUBMITTED` / `NODE_ARRIVED` / `NODE_PASSED`（建议在"到达审核节点"时推 `NODE_ARRIVED`） |
| `version` | ✅ | **单据版本号，每次修改必须 +1**（否则幂等会吃掉你的重推） |
| `form.*` | ✅ | 业务字段，规则 DSL 用 `$form.xxx` 引用 |
| `attachments[].ocr_struct` | | OCR 结构化结果，规则用 `$attachment.ocr.xxx` 引用 |
| `applicant` | ✅ | 提单人信息（路由打回时用） |
| `ctx` / `std` | | **外部系统补充上下文**，规则用 `$ctx.*` / `$std.*` 引用（如制度阈值、项目等级、部门） |
| `submitted_at` | | 单据提交时间，RAG 制度检索按此日期过滤生效期条款 |

> **字段映射现状**：`connector_config.field_mapping` 字段**已在表结构预留，但当前无代码消费**。
> 因此你必须**按上式直接发 Canonical 结构**，或在你的系统侧写一层适配器做字段转换。
> 后者也是推荐做法——适配逻辑放在你这边，升级更自由。

### 2.4 幂等

```
idempotency_key = sha256( source_code | instance_id | current_node | event_type | version )
```

- 同一单据 + 同一节点 + 同一事件类型 + 同一版本 → **只审一次**；
- 重复推送返回 HTTP 202 + `deduplicated: true` + **原 task_id**（不新建任务）；
- 若单据内容变了要重审，**请把 `version` +1**（这也是版本号存在的意义）；
- 网络重试可放心重发同一包。

### 2.5 响应与错误码

| 状态 | body / 含义 |
|---|---|
| **202** | `{"task_id":"...","deduplicated":false,"status":"accepted","dispatch":"arq"\|"inline"}` |
| 202 | `{"task_id":"原id","deduplicated":true,...}` —— 幂等命中 |
| **400** | `invalid json` —— 请求体不是合法 JSON（注意：签名是对原始字节算的） |
| **401** | `missing signature headers` / `bad timestamp` / `timestamp replay window exceeded` / `signature mismatch` |
| **404** | 路径不对（`source_code` 拼错不会 404，密钥回退全局默认后可能 401） |
| **422** | `instance.instance_id required` |

## 3. 出站协议（ai-auditor → 你）

审核完成后，若该决策需要动作，ai-auditor 会 POST 到你配置的端点：

```
POST {flow_profile.writeback_config.http_endpoint}
Content-Type: application/json

{
  "tier": "FULL_API",
  "action": "RETURN",
  "target_node": "applicant",
  "task_id": "ff4628b14252438696297aced8cbcbd1",
  "instance_id": "IT-1ff1ccfd",
  "comment": "【数字人审核】发现以下问题：\n- HIGH_AMOUNT（major）：单据金额 500000.0 元超过 10 万元，须人工审核",
  "problem_codes": ["HIGH_AMOUNT"]
}
```

> 以上是**实测抓包**的真实 payload（非示例）。

### 3.1 你要用哪些字段

| 字段 | 语义 | 你的动作 |
|---|---|---|
| `instance_id` | 定位单据（**主键**） | 用它在自己库里找到该单 |
| `action` | 处置动作 | 见下表 |
| `target_node` | 目标节点 / 处理人角色 | 打回或加签到此节点 |
| `comment` | 意见正文（已带"数字人"署名） | 作为审批意见写入 |
| `problem_codes` | 命中问题码 | 用于分类、统计、路由校验 |
| `tier` | 本次实际生效的档位 | 用于日志与降级监控 |

| action | 含义 | 建议实现 |
|---|---|---|
| `RETURN` | 打回指定节点 | 退回 `target_node`（默认提单人 `applicant`） |
| `ESCALATE` | 加签 / 转办 | 加签到 `target_node`（如财务经理） |
| `COMMENT` | 仅附加意见 | 写一条意见，**单据继续正常流转** |
| `SAMPLE_CHECK` | 自动通过后随机抽检 | 标记为待抽检，通知质检 |

### 3.2 回写档位与降级链

```
FULL_API  ──失败──▶  COMMENT_ONLY  ──失败──▶  IM_ONLY
（调 API 打回/加签）    （意见附件方式追加）     （推 IM 机器人看板，线下兜底）
```

- 起始档位由 `flow_profile.writeback_tier` 决定，逐级降级，**任一档成功即停止**；
- 每次尝试的返回都记录在 `escalation_log.writeback_response`，状态见 `writeback_status`：

| writeback_status | 含义 |
|---|---|
| `applied` | 首档成功 |
| `degraded` | 降级后成功 |
| `failed` | 全档失败（**需人工关注**） |
| `skipped_shadow` | shadow 模式，只审不动 |
| `no_action` | 决策无需动作（如高置信建议通过） |

**你的端点只需返回 HTTP < 400 即视为成功**（body 不解析）。回写失败**不会阻塞**审核流水线。

### 3.3 回写端点最小实现

```python
# 你的 OA 侧（示例：Flask）
@app.post("/ai-audit/writeback")
def writeback():
    d = request.get_json()
    inst = find_instance(d["instance_id"])
    if d["action"] in ("RETURN", "ESCALATE"):
        inst.move_to(d["target_node"], comment=d["comment"])
    elif d["action"] == "COMMENT":
        inst.add_comment(d["comment"])          # 不中断流转
    elif d["action"] == "SAMPLE_CHECK":
        inst.flag_sample_check()
    return {"ok": True}, 200
```

## 4. 放权四档与决策语义

`flow_profile.mode` 决定"数字人能不能动单子"：

| mode | 行为 | 回写 |
|---|---|---|
| `shadow` | 只审不动，结果仅存档（影子评测期） | 不发起（`skipped_shadow`） |
| `advisory` | 只给建议意见，全部人工继续 | `COMMENT`（不改变流向） |
| `semi_auto` | 满足条件时可自动通过；问题单据按路由表处置 | `PASS`→抽检；问题→`RETURN`/`ESCALATE` |
| `full_auto` | 同上，放权范围更宽 | 同上 |

**自动通过的门槛**（三者同时满足才算 `auto_allowed`）：

```
mode ∈ {semi_auto, full_auto}  AND  auto_pass_enabled = true  AND  amount ≤ amount_cap
```

决策级别（你能在查询接口 / 回写里看到）：

| level | 触发条件 |
|---|---|
| `REJECT` | 任一规则 findings 为 **major / critical**（硬违规，矩阵最高优先级） |
| `ESCALATE` | 需上层介入（按路由表 `ESCALATE`） |
| `ADVISORY` | 有轻微问题或 LLM 置信度不足 → 附意见人工继续 |
| `PASS` | 无 finding + LLM 高置信 + 在放权范围内 |

**灰度放权建议路径**：`shadow`（收集一致率 ≥85%）→ `advisory` → `semi_auto`（先小额、置 `amount_cap`）→ `full_auto`。
任何时候把 `mode` 改回 `shadow` 即刻停手，不影响你的单据流转。

## 5. 端到端对接步骤

```
① 建连接器      INSERT connector_config (source_code, webhook_secret, ...)
② 建流程档案    INSERT flow_profile (mode, writeback_tier, writeback_config, route_table)
③ 配审核规则    INSERT policy_rule   ← 或用参考实现自带的演示规则
④ 实现回写端点  你的系统加一个 POST 接口
⑤ 联调自测      python tools/onboard_check.py listen / publish
⑥ 影子试运行    mode=shadow 跑 1~2 周，比对一致率
⑦ 逐步放权      advisory → semi_auto (amount_cap) → full_auto
```

### 关心的查询 / 运维接口

| 接口 | 用途 |
|---|---|
| `GET /api/v1/audit-tasks/{task_id}` | 查任务状态 / findings / decision |
| `GET /api/v1/runs/{run_id}/events?after_seq=N` | 事件流增量拉取（三层内核执行轨迹） |
| `GET /api/v1/runs/{run_id}/capability-calls` | 能力调用留痕（预算/延迟审计） |
| `POST /api/v1/audit-tasks/{run_id}/resume` | **人工处理挂起单**（HMAC 验签 + resume_token） |
| `PUT /api/v1/flows/{code}/sop` | 装载/更新该流 SOP |

### 挂起（human_gate）场景

若 SOP 里含人工确认节点，任务会挂起（`status = awaiting_human`），此时**不出决策**。
你的系统需拉取待办并调 `resume` 恢复：

```json
POST /api/v1/audit-tasks/{run_id}/resume
{ "action": "OVERRIDE_PASS",          // 或 OVERRIDE_REJECT | SUPPLY_MATERIAL | COMMENT
  "resume_token": "<human_task.resume_token>",
  "operator": "u1001",
  "payload": { "patch_fields": {"amount": 3000}, "comment": "已补充说明" } }
```

`SUPPLY_MATERIAL` 会合并字段补丁并**只重跑受影响的帧**（未变帧标记 `reused`，不重复调用 LLM）。

## 8. 常见问题

| 现象 | 原因 |
|---|---|
| `401 signature mismatch` | ①签名后重新序列化了 body；②timestamp 与头里不一致；③密钥用错（connector 专属密钥 vs 全局默认） |
| `401 timestamp replay window exceeded` | 时钟不同步（差 > 300s），或用了毫秒时间戳 |
| `202` 但反复 `deduplicated: true`，看不到新审核 | 单据改了但 `version` 没 +1 |
| `422 instance.instance_id required` | `instance` 层级写错（例如把 instance_id 放在顶层） |
| 任务永远停在非 `decided` | worker 未启动 / `queue_mode` 配置问题 / 查看 `docker compose logs worker-1` |
| 决策出了但单据没变化 | `writeback_config.http_endpoint` 未配置（走了 Mock，只记录不真发）；或对端返回 4xx/5xx 触发降级 |
| 想让数字人「闭嘴只看」 | `mode` 改 `shadow`：审核照跑，`writeback_status=skipped_shadow`，不动单据 |
