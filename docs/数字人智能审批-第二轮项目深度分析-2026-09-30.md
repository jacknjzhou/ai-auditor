## 一、逐项目深度分析

### 1.1 Octop（腾讯云）⭐5,921 — 自托管多 Agent 中枢

**定位修正**：第二轮文档称其为"个人/小团队 Agent 中枢"，本轮 README 核实后确认——它同时有相当多**企业级治理特性**，定位应为"自托管的个人/家庭/小团队 AI 助手平台，具备企业级安全雏形"。

**架构（官方 README 原文核实）**：

```
OctopServer（单进程）
 ├─ DatabasePool            SQLite(WAL) 默认 / PostgreSQL 可选
 ├─ SharedServices          DI 根容器
 ├─ ExpertCatalog           启动时扫描专家库
 ├─ UserManager
 │   └─ HarnessAgentManager（每用户）
 │       └─ AgentRuntime（每 Agent）
 │           ├─ HarnessAgent      Agent 运行时（octop-harness 独立仓库）
 │           ├─ HarnessProcessor  IM / UI / cron 统一入口（无外部消息队列）
 │           ├─ ChannelManager    IM 连接（octop-gateway 独立仓库）
 │           └─ CronManager       APScheduler
 └─ FastAPI app (uvicorn)
```

- **技术栈**：Python 3.12+ / FastAPI + uvicorn / React 18 + TS + Vite + Ant Design / APScheduler；有官方 ADR 文档（001 单进程模型、002 数据库后端）。
- **组件全部独立开源**：octop-harness（模型路由/工具/skill/会话检查点）、octop-gateway（多平台 IM 桥接，归一化消息管线）、octop-memory（分层记忆+FTS）、octop-browser（CDP 自动化+持久 profile）——**这是二开最友好的部分，比单一 monorepo 边界清晰**。

**与审批场景直接相关的发现（第二轮文档未覆盖）**：
- **内置 Tool Approval 与 shell 命令护栏**：`~/.octop/security/tool_guard/` 下用户可编辑 allow/deny 规则；敏感数据出 workspace 前有 **PII 脱敏**。这已经是"高风险动作卡点"的雏形——OA 审批门控可挂在 tool approval 钩子上，而不是从零自建。
- **钉钉/飞书均为一等通道**（App Key/Secret 配置即用），通道归一化经 octop-gateway。
- **ACP 双向**：外部 IDE 可调 Octop Agent；Octop 也可外委 OpenCode/CodeBuddy/Claude Code/Codex（带 permission gates）。
- 部署支持 `octop service start` 注册 **systemd/launchd/Windows 服务**（符合你不用 Docker 的偏好）；SQLite→PostgreSQL 可平滑切换。
- Roadmap 中的 AgentTeams（协调者调度多专家）仍在 Beta，**多步任务的编排成熟度不如 Dify**。

**风险**：issues 618 偏多（相对其规模）；增长快意味着 API/配置面变动频繁，追新有维护成本。

### 1.2 Fay ⭐13,552 — 数字人连通业务系统的事实标准

**本轮新信息（README 实测）**：
- **三个版本已合并为 1 个**（原 2.5d/3d/移动版分裂已终结），统一为" Fay 数字人框架"。
- 官方接口清单比第二轮文档更完整：**文字交互 / 语音交互 / 数字人驱动 / 管理控制 / 自动播报 / 意图** 六类接口，支持单片机、App、网站、大屏、三方业务系统接入。

### 1.3 CyberVerse ⭐1,684 — 实时数字人视频 Agent

**本轮新信息（README 实测）**：
- ⚠️ **组织归属注意**：README 徽章与 clone 地址均指向 `dsd2077/CyberVerse`，我们实测 star 的是 `Lynpoint/CyberVerse`——两仓存在镜像/迁移关系，引用时建议标注双仓。
- 数字人驱动模型为 **SoulX-FlashHead 1.3B / SoulX-LiveAct**（Soul AI Lab 开源），本地实时门槛：FlashHead 需 RTX 5090（512×512@25fps 双卡）；LiveAct 需 RTX PRO 6000。**没有本地 GPU 可走云 API**：百度曦灵 / 讯飞数字人 / Vidu S1。
- **原创 RTP 指标**（elapsed / (frames/fps)）用于自检实时性：RTP<1 才能实时流式——README 甚至给出性能调优手册（降分辨率/加卡/FP8-FP4 GEMM/SageAttention）。
- 技术栈比预期重：**Go 1.25（API 服务器 + pion/WebRTC）+ Python 3.10（推理）+ Node 前端三进程**；LiteLLM 插件统一 100+ LLM。
- PersonaAgent（前台保对话流畅）+ SubAgent（后台长任务异步）分工确认，与"数字人前台受理 + 后台 Agent 干活 + 人审"的审批展示原型高度契合。

**审批视角**：表现层天花板最高，但工程门槛也是所有项目里最高的（CUDA 12.8、vllm、conda、gRPC 全家桶）。纯语音模式（`avatar.enabled: false`）可免 GPU，先跑语音再上视频是合理路径。

**octo-server 深挖（PR/目录级核实）**：
- 模块划分：`user / group / botfather / bot_api / bot_provision / channel / space / oidc / robot`；BotFather 支持 OBO（on-behalf-of）代行式 bot 铸造。
- **Agent 接入三步链路（PR #492）**：Web onboarding 懒创建 `uk_` 前缀 API key → fleet/matter 验证 → daemon 用 key 换 bot_token。daemon 安装走 npm。
- **IM 卡片审批流（PR #793，本轮最重要的审批证据）**：Docs 访问请求 → IM 生成可操作卡片 → 审批人 approve/deny → **卡片原位终态化（terminalize in place），且不给申请人发第二张终态卡**——"审批人卡片是唯一 IM 结果面"是明确的产品决策，这是开箱即用的 IM 内审批范式。
- **人际关系授权**：联系人披露需本人/好友/同 Space 活跃成员，仅同群不授予（PR #919）——组织级信息分级的细粒度设计。
- 部署依赖：**MySQL 8.0 + Redis 7（要求 EVALSHA）+ WuKongIM**，非 K8s 也可裸机部署（符合你的偏好）。
- 开发流程人机协作：PR 强制 COMPREHENSION 三问（改了什么/破坏什么/如何证明），大量 AI 联合署名提交——它自己就是"AI 员工在真实企业代码库工作"的活样本。

**审批视角**：Octo 是唯一把**审批卡片、bot 权责（名片+工作记录）、组织归属**三者做进同一个 IM 底盘的开源生态，Apache-2.0 + Go 后端自托管友好。缺点：Lobster 编排细节文档不足（官方仅一句描述），生态庞大导致学习曲线陡。

### 1.5 DeskClaw（nodeskclaw）⭐758 — 团队版企业运行平台

**本轮新信息（README 实测）**：

### 1.6 markfulton/ai-employees ⭐476 — 8 岗位 AI 员工 + 审批窗口（审批设计最佳参考实现）

**本轮深挖到的完整文件契约**（每个员工就是一个纯文本文件夹）：

```
gtm-engineer/
  INSTALL-PROMPT.md     Agent 一次性自举安装指令
  ROLE.md               角色人格与思维方式
  SCHEDULE.md           例程时间表（含时间窗口）
  RELEASES.md           ★ 渠道放行清单——"你已经放行的渠道"，出厂为空
  routines/<id>/SKILL.md  每个例程一个文件夹
```

**审批/护栏设计（本轮核实到的全部机制）**：
- **双护栏**：① 所有 send/post/submit/publish/spend 一律**暂存等待你的点击**（veto window，社媒员工明确带"人工审批窗口"）；② `RELEASES.md` 是唯一"渠道放行"开关——只有你手动写入的渠道才免审。
- **红线（写死在 STANDARD v1.4，共 7 条 LAW）**：永不创建账号/输密码/过验证码/接受条款。
- `scripts/guard.mjs` 前置于每个例程（D5），失败运行会记入 runlog；错过窗口（机器休眠）触发时自检"工作已完成"则跳过（幂等）。
- **brief.deliver 机制**：晨间简报只投递到"成员自己的线程/地址"（delivery ≠ send）——投递行为本身不受审批门控，外发行为才受。
- 例程五问（STANDARD 4 节）：trigger / frequency / output / silence / stop——**建议直接抄进你的 Agent 例程设计规范**。
- 跨 11 种 Harness 执行（Claude Code、OpenClaw、Hermes、OpenCode、Codex、Grok Bot、Antigravity、Pi、Cline、Qwen Code、DeepSeek、Muse、Dots），本身就是 Claude Code 插件（`/plugin marketplace add markfulton/ai-employees`）。
- 8 角色：GTM 工程师(8) / SEO-AEO(8) / Web 开发(8) / 社媒(7) / 广告投放(7) / 销售(7) / 客户满意(8) / 幕僚长(7)，共 60 例程；成本实测约为 Claude Max 计划用量的 6%。

**结论不变且加强**：这是"AI 起草 + 人终审"最轻、最可抄的实现。零平台依赖、MIT、纯约定——**把它的 RELEASES.md + veto window + 例程五问移植到你的桌面 Agent（钉钉/飞书审批场景）是性价比最高的一步**。

### 1.7 Dify v1.13.0 Human Input 节点 — 官方 HITL 工作流原语（文档级核实）

**机制全貌（官方 docs + v1.13.0 Release Discussion 核实）**：
- **提交方式**：Web App（终端用户表单；Trigger 启动的流不可用；可通过 Service API 驱动表单生命周期）/ **Email**（收件人无需 Dify 账号，持链接即可审批；可发自定义主题/正文给工作区成员+外部邮箱）。首个响应到达即关闭请求。
- **表单字段四类**：Paragraph（可预填上游 LLM 输出，编辑后回传）/ Select（单选，选项可来自 array[string] 变量）/ Single File（图 10MB/文档 15MB/音频 50MB/视频 100MB）/ File List（≤10 个）。必填未填时决策按钮禁用；全部值经 `__rendered_content` 变量下游可用。
- **决策按钮**：每按钮 = `__action_id` + `__action_value`，路由到不同分支——"批准/退回重生成/转发升级"官方模板全齐。
- **超时**：节点默认 3 天，可接超时分支（提醒/转办）；全局上限 `HUMAN_INPUT_GLOBAL_TIMEOUT_SECONDS=604800`（7 天）；超时检查任务每分钟跑一次（`HUMAN_INPUT_TIMEOUT_TASK_INTERVAL`）。
- **架构（v1.13.0 重构）**：流式 Workflow/Chat 执行迁入 Celery worker，暂停/恢复全部经 Celery，事件经 Redis Pub/Sub 回流；高吞吐场景官方强制建议 **sharded PubSub + Redis Cluster** + 独立 `PUBSUB_REDIS_URL`；新增必需队列 `workflow_based_app_execution`（**不配则 HITL 恢复流程直接不工作**——自托管升级的最大坑点）；表单提交限流 30 次/60 秒/IP。

**审批视角**：低代码赛道把审批做成了工作流一等原语，"审批人非技术人员 + 流程相对固定"场景下自研性价比最低。代价是运维复杂度：Celery 队列 + Redis 集群 + 每分钟超时扫描任务。

### 1.8 multi-agent-orchestration — 确认 404，仅保留架构思想

## 三、结合你的场景（桌面 Agent + 钉钉/飞书 OA 审批 + 非 Docker 部署）

### 分层选型结论

1. **审批门控内核**：`LangGraph interrupt/Command(resume)`（事实标准）+ UniEmployee approvals.db 表结构（TTL/积压上限/权限三件套）。审计日志采用"只记结构化元数据、不存原文与 PII"的不可变追加模式。
